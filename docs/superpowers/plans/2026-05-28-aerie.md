# Aerie Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build a macOS-native SwiftUI dashboard that surfaces local git state and open PRs across ~50 git repos, with multi-account `gh` CLI auth, smart polling, and an in-process MCP HTTP server so parallel Claude Code sessions can share Aerie's cache and trigger its actions.

**Architecture:** SwiftUI front-end + actor-isolated service layer + GRDB SQLite cache. Single source of truth: services write the cache, the UI subscribes to the cache. The MCP server is an in-process Hummingbird HTTP listener that re-uses the same service layer the GUI uses, so writes from GUI and MCP can never race.

**Tech Stack:** Swift 5.9 / SwiftUI / Swift Concurrency · `SwiftGitX` (modern Swift wrapper over libgit2; async/await, Swift 6 ready) · `URLSession` + `Codable` (GitHub REST + GraphQL) · `GRDB` (SQLite) · `Hummingbird` (HTTP server for MCP) · `swift-snapshot-testing` (view snapshots)

**Spec:** `docs/superpowers/specs/2026-05-28-aerie-design.md` — read this first. It contains the data model, persistence schema, error matrix, and the full visual contract (§9).

**Design reference:** `docs/superpowers/design/v2/` — the JSX prototypes from Claude Design. Use these for pixel-perfect color, sizing, spacing. Do **not** copy their internal structure — translate to idiomatic SwiftUI.

---

## Conventions

- **Language**: Swift 5.9. Target macOS 14 (Sonoma) minimum so we can use `@Observable` and the modern `SwiftUI` window APIs.
- **TDD**: services and view models get a failing test first. SwiftUI views get a snapshot test after the visual is approved.
- **Commits**: small, often. One commit per task by default. Use Conventional Commits style (`feat:` `fix:` `refactor:` `test:` `docs:` `chore:`).
- **File layout**: `Sources/Aerie/` for production code, `Tests/AerieTests/` for tests. SwiftUI views under `Sources/Aerie/Views/`, services under `Sources/Aerie/Services/`, models under `Sources/Aerie/Models/`, persistence under `Sources/Aerie/Persistence/`.
- **Run all tests**: `swift test` or `xcodebuild test -scheme Aerie`.
- **Working dir**: all paths in this plan are relative to the repository root (`/Users/carlosli/work/Aerie`).

```swift
import SwiftUI

/// Applies the Aerie glass treatment used on cards, dialogs, and the window.
/// `backdrop: blur(40px) saturate(160%)`, `border 1px var(--glass-line)`,
/// `inset 0 1px 0 0 var(--glass-highlight)`.
struct GlassModifier: ViewModifier {
    enum Variant { case window, card, dialog }
    let variant: Variant

    func body(content: Content) -> some View {
        let blur: CGFloat = variant == .dialog ? 48 : 40
        let cornerRadius: CGFloat = variant == .window ? AerieMetric.radiusWindow : AerieMetric.radiusCard
        return content
            .background(
                ZStack {
                    AerieColor.glass1
                    VisualEffectBlur(material: .hudWindow, blendingMode: .behindWindow)
                        .opacity(blur / 50.0)
                }
            )
            .clipShape(RoundedRectangle(cornerRadius: cornerRadius, style: .continuous))
            .overlay(
                RoundedRectangle(cornerRadius: cornerRadius, style: .continuous)
                    .strokeBorder(AerieColor.glassLine, lineWidth: 1)
            )
            .overlay(
                RoundedRectangle(cornerRadius: cornerRadius, style: .continuous)
                    .strokeBorder(AerieColor.glassHighlight, lineWidth: 1)
                    .mask(
                        LinearGradient(
                            stops: [.init(color: .white, location: 0), .init(color: .clear, location: 0.05)],
                            startPoint: .top, endPoint: .bottom
                        )
                    )
            )
    }
}

extension View {
    func glass(_ variant: GlassModifier.Variant = .card) -> some View {
        modifier(GlassModifier(variant: variant))
    }
}

/// NSVisualEffectView bridge.
struct VisualEffectBlur: NSViewRepresentable {
    var material: NSVisualEffectView.Material
    var blendingMode: NSVisualEffectView.BlendingMode
    func makeNSView(context: Context) -> NSVisualEffectView {
        let v = NSVisualEffectView()
        v.material = material
        v.blendingMode = blendingMode
        v.state = .active
        return v
    }
    func updateNSView(_ nsView: NSVisualEffectView, context: Context) {
        nsView.material = material
        nsView.blendingMode = blendingMode
    }
}
```

```swift
import Foundation

protocol SubprocessRunner {
    /// Returns (stdout, stderr, exitCode). Throws on launch failure only.
    func run(_ command: String, _ args: [String]) async throws -> (String, String, Int32)
}

struct LiveSubprocessRunner: SubprocessRunner {
    func run(_ command: String, _ args: [String]) async throws -> (String, String, Int32) {
        let p = Process()
        p.executableURL = URL(fileURLWithPath: "/usr/bin/env")
        p.arguments = [command] + args
        let outPipe = Pipe(); p.standardOutput = outPipe
        let errPipe = Pipe(); p.standardError  = errPipe
        try p.run()
        return await withCheckedContinuation { cont in
            p.terminationHandler = { proc in
                let out = String(data: outPipe.fileHandleForReading.readDataToEndOfFile(), encoding: .utf8) ?? ""
                let err = String(data: errPipe.fileHandleForReading.readDataToEndOfFile(), encoding: .utf8) ?? ""
                cont.resume(returning: (out, err, proc.terminationStatus))
            }
        }
    }
}
```

```swift
protocol AuthService: Actor {
    func bootstrap() async throws -> AuthBootstrapResult
    func token(for accountId: UUID) async throws -> String
    func allAccounts() async -> [GitHubAccount]
}

enum AuthBootstrapResult: Equatable {
    case ok(accounts: [GitHubAccount])
    case ghMissing
    case noAuth
}

actor LiveAuthService: AuthService {
    private let runner: SubprocessRunner
    private var accounts: [GitHubAccount] = []
    private var tokens: [UUID: String] = [:]

    init(runner: SubprocessRunner = LiveSubprocessRunner()) { self.runner = runner }

    func bootstrap() async throws -> AuthBootstrapResult {
        // detect gh exists
        let (whichOut, _, whichRC) = try await runner.run("which", ["gh"])
        if whichRC != 0 || whichOut.isEmpty { return .ghMissing }

        // gh auth status
        let (out, _, _) = try await runner.run("gh", ["auth", "status"])
        let parsed = GhAuthStatusParser.parse(stdout: out)
        if parsed.isEmpty { return .noAuth }

        // for each, fetch token via gh auth token
        var accs: [GitHubAccount] = []
        var toks: [UUID: String] = [:]
        for p in parsed {
            let acct = GitHubAccount(id: UUID(), login: p.login, host: p.host)
            let (tokOut, _, _) = try await runner.run("gh",
                ["auth", "token", "--hostname", p.host, "--user", p.login])
            toks[acct.id] = tokOut.trimmingCharacters(in: .whitespacesAndNewlines)
            accs.append(acct)
        }
        self.accounts = accs
        self.tokens = toks
        return .ok(accounts: accs)
    }

    func token(for accountId: UUID) -> String? { tokens[accountId] }
    func allAccounts() -> [GitHubAccount] { accounts }
}
```

## Cross-cutting concerns

These are non-task items the implementer should keep in mind through the whole plan:

- **Per-snapshot stability**: SwiftUI snapshots can drift across macOS minor versions. Pin the test environment to a single macOS SDK in CI.
- **GRDB on actor**: `dbQueue` is `Sendable`; `AppDatabase` is an actor; DAOs can be non-actor structs that take an `AppDatabase` reference, OR DAOs can themselves be actor methods on `AppDatabase`. The choice doesn't matter as long as **all writes serialize through the queue** (GRDB handles this internally).
- **Codable + database**: each row's `payload_json` column stores the entity's `JSONEncoder().encode(entity)` blob. Decoders should be permissive (`.convertFromSnakeCase` etc.) so future spec additions can land without migrations.
- **Working directory access in tests**: SwiftGitX integration tests need real on-disk repos. Use `NSTemporaryDirectory()` + cleanup. SwiftGitX initializes its libgit2 runtime lazily on the first `Repository` open and shuts it down when the last `Repository` is freed; tests should keep at least one `Repository` reference alive for the duration of the test method.

## Known issues (Phase 21 smoke)

The following are wired through the service / view layer individually but
are not yet composed into the running app shell. They block the full
end-to-end smoke described in Task 21.3 and are tracked as follow-ups
for a post-implementation polish pass:

- **Main shell content**: `AerieApp.AppRoot` currently routes to either
  `FirstRunRoot` or the placeholder `ContentView()`. The ok-branch needs
  to render `AppFrame { ... }` with `PRsScreen` / `ReposScreen` swapped
  by `AppViewModel.activeTab`, and the `ToastManager` overlay attached.
  Each piece is built and tested independently; this is a wiring task.

- **MCP consent gating**: `MCPConsentDialog` exists with a snapshot, but
  `AerieApp.AppRoot` doesn't yet show it when `mcp.consent_decision == "unset"`.
  Wire after the main shell is up.

- **`~/.claude/.mcp.json` integration**: `ClaudeCodeConfigWriter` is in
  place; `MCPSettingsViewModel.setAutoRegister` calls it. On startup,
  the app should also call `upsertAerie` when consent is granted +
  `autoRegisterOn` is set.

- **Drag-reorder for Settings → Repositories**: `RepositoriesViewModel.reorder(from:to:)`
  is implemented + tested; the SwiftUI `.onDrag` / `.onDrop` plumbing on
  `RepoSettingsRow` / `RepositoriesScreen` is the missing piece.

- **Polling pipeline integration**: `PollingScheduler.attachFocusObserver`
  is wired through `AppFocusObserver`, but the per-repo `refresh` closure
  needs to call `GitService.readStatus` + `MultiAccountAPI.listOpenPRs` and
  upsert into the cache DAOs. The component pieces exist; the orchestration
  closure is the gap.

- **Polling → `LiveIndicator` next-tick countdown**: `LiveIndicator` reads
  `AppViewModel.nextTickInSeconds`. `PollingScheduler` doesn't yet publish
  the next-tick `Date`; the orchestration closure should update it on
  each `tickOnce`.

- **`gh --version` banner**: `AccountsScreen` accepts a `ghVersion` parameter;
  the integration layer should call `gh --version` via `LiveSubprocessRunner`
  at startup and inject the result.

- **AppViewModel `nextTickInSeconds` decrement**: timer-driven; either drive
  from `PollingScheduler.nextTickAt` and a 1Hz Timer, or read directly off
  the scheduler. Decision deferred until orchestration lands.

All of the above are integration wiring on top of feature-complete pieces.
No new model / DAO / service work is required to close them.
